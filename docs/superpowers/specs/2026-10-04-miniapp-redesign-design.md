# 蓓贝婴童小程序视觉改版 — 设计文档

- 日期：2026-10-04
- 范围：`miniapp/` 的 5 个 tab 主页面 + 公共组件 + 主题 token，**加 `backend/` 的三项修复**
- 状态：待评审（2026-10-04 修订：新增后端范围，见 §9）

---

## 1. 背景与目标

### 现状

蓓贝婴童小程序（uni-app + Vue3 + TS + uview-plus，微信小程序）目前 `pages.json` 注册 **20 个页面**，`src/` 下 **12,841 行**。视觉上的主要问题（数字均为实测）：

1. **emoji 当图标** —— **19 个文件**里散着 **31 种 emoji、共 76 处**（🧸🔍🛒📦📋🔐💳…）。跨机型渲染不一致，是"不像成熟产品"的主因
2. **页面骨架雷同且平** —— 分区标题靠一条竖色条区隔，卡片层级弱
3. **底栏点了没反馈** —— `static/icons/` 下 10 个 PNG（5 组常态 + `-active` 选中态）**都齐全**，但 `pages.json` 的 `selectedIconPath` 全指向非选中图标

### 目标

以 `素材/1.png`、`素材/2.png`（星巴克小程序截图）的**布局语言**为参照，重建蓓贝婴童的视觉体系：

- 品牌色头图区 + 悬浮白色圆角卡片
- 分区大标题（无装饰条）
- 满宽横图卡
- 底部凸起圆 tabBar

**只借布局，不借配色** —— 品牌主色保持珊瑚橙粉 `#e16531`。

### 关键前提（影响设计取舍）

改版调研期间对生产环境 `https://baby.mx.yn.cn/api/v1` 做了实测，发现三类缺陷。它们直接决定了「空状态」和「演示数据」不是锦上添花，而是**承重结构**。

**① 三个接口是坏的**

| 接口 | 现象 | 根因 |
|---|---|---|
| `GET /promotions/active` | **HTTP 500** | `promotions` 表从未被创建 |
| `GET /cases/tags/styles`、`/cases/tags/categories` | **HTTP 422** | 后端只有 `/cases/tags`，这两个路径被 `/{case_id}` 路由捕获 |
| `GET /cases/{id}/like`、`POST /auth/logout` | 后端不存在 | 前端单方面调用了它们 |

**② 三张表有模型、没有迁移**

模型定义了 13 张表，迁移只建了 10 张。缺 `promotions`、`credit_bills`、`knowledge_entries`。

注意：部署脚本 `deploy/deploy-prod.sh:81` **确实在执行** `alembic upgrade head`，但它无事可做——**迁移文件根本没写**。所以这不是"忘了跑迁移"，重跑修不好，必须补写迁移。

**③ 零数据、零种子脚本**

商品 total = 0、分类 = []、案例 total = 0。全库唯一的建数据脚本是 `deploy/create_admin.py`（建一个管理员），不灌任何商品/案例/促销。

**结论：** 现状下 5 个 tab 页看到的会是空壳加一个 500。本次必须同时交付"内容饱满"和"空数据"两种状态，并把上面三类缺陷修掉。

## 2. 已确认的决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 参考程度 | 只借布局，保留珊瑚橙粉 `#e16531` | 星巴克是绿色咖啡品牌，我们是母婴 B2B，配色照搬会丢掉品牌识别 |

| 4 | 数据策略 | 精致空状态 + 开发期演示数据（可开关） | 空状态是用户真实会看到的；演示数据用于验收设计满负荷的样子 |
| 5 | 实现路线 | 设计系统先行（token → 公共组件 → 页面） | 后续 15 个子页面可直接复用组件 |
| 6 | 首页信息架构 | 入口聚合型（照素材） | 品牌感强，会员/权益/活动有地方摆 |
| 7 | 「设计案例」区 | 横滑横图卡，位置在品牌活动之前 | 分区高约 250rpx vs 竖排约 430rpx，B2B 客户更快摸到货 |
| 8 | AI 页命名 | 小暖AI → **蓓贝客服**；首页「小暖推荐」→ **蓓贝推荐** | — |
| 9 | tab 顺序 | 首页 / 案例 / **[蓓贝客服]** / 商品 / 我的 | 客服居中做成凸起圆，一个凸起占一个专属位置 |

| 11 | 凸起圆 | 实心 `#e16531` + 白色图标，直径 **128rpx**，标准底栏高，**高出 36rpx**，**无描边** | 见 §6 |
| 12 | 客服页底栏 | **不显示**底栏 | 输入栏占住底部，聊天页保持沉浸 |
| 13 | 底栏图标 | 换成 `u-icon` 字体图标 | 全站一套图标体系，选中态靠 `color` 切换，不再维护两份 PNG |
| 14 | 后端修复 | **只修「让 5 个 tab 页能显示真实数据」所必需的三项**，其余已知缺陷记录不修 | 见 §9。不做这个的话，首页的设计案例和品牌活动分区在真机上是空的或 500 |
| 15 | 积分抽奖 | **本轮不做** | 全库零代码，是独立新功能，需要自己的 spec → 计划 → 实现周期 |

## 3. 设计语言

### 3.1 颜色

主色不变，新增几个 token：

```scss
--color-primary: #e16531;          // 保持不变
--color-primary-light: #f0916a;    // 新增：头图渐变终点
--color-primary-mid: #f5b28f;      // 保留
--color-ink: #2B2320;              // 新增：横图卡胶囊按钮底色（深棕，比纯黑贴暖调）
--color-on-primary: #ffffff;
```

`--color-ink` 的由来：素材里横图卡的按钮是纯黑配绿底，很跳；配珊瑚橙粉会发冷，改用深棕。

### 3.2 圆角（**需要重校准**）

现有 token 偏大（`--radius-lg: 20px` = 40rpx），素材实测卡片圆角约 24–28rpx：

```scss
--radius-sm: 8rpx;      // 标签、小徽章
--radius-md: 16rpx;     // 输入框
--radius-lg: 28rpx;     // 内容卡片（原 40rpx）
--radius-hero: 32rpx;   // 头图/横图大卡
--radius-pill: 999rpx;  // 胶囊
```

> ⚠️ **这是全局 token，会同时影响不在本次范围内的 15 个子页面。** 这是有意为之（视觉刷新本来就该全站一致），但必须在实现阶段做一次全页面视觉回归，确认没有压字/错位。

**单位从 px 改成 rpx。** 现有 `theme.scss` 的圆角/阴影写的是 px（`--radius-lg: 20px`），上面改成 rpx。rpx 是小程序的响应式单位，750rpx = 屏宽，在不同机型上等比缩放，这正是设计稿要的效果；px 是固定值，在大屏上会显得偏小。这是**语义变更**，不是单纯的数值调整 —— 一并纳入视觉回归范围。

### 3.3 阴影

素材的卡片阴影很轻，现有 `--shadow-card: 0 4px 20px rgba(0,0,0,.06)` 基本可用，微调：

```scss
--shadow-card: 0 4rpx 16rpx rgba(74, 55, 40, 0.06);   // 带暖调，不纯黑
--shadow-hero: 0 8rpx 24rpx rgba(225, 101, 49, 0.18); // 凸起圆
--shadow-float: 0 -2rpx 12rpx rgba(0, 0, 0, 0.05);    // 底栏上沿
```

### 3.4 字号与间距

保持现有 `--font-*` / `--space-*` 不变。分区大标题用 `--font-xl`（36rpx）加粗 —— 素材的「星礼点亮每天」明显比正文大一级。

### 3.5 分区标题样式变更

```
现在：│ 小暖推荐            ← 4px 竖色条 + 32rpx/600
改为：  蓓贝推荐            ← 无装饰条 + 36rpx/700
```

竖色条删除。层级靠字号和字重建立，这是素材的做法。

## 6. 自定义 tabBar

### 6.1 为什么必须换

`pages.json` 的原生 tabBar：

- 画不出凸起圆
- 无法给**单个** tab 去掉文字（微信只支持统一配置）

### 6.2 几何规格

素材实测（414px 宽截图 → 750rpx）与我们的取值：

| 项 | 素材 | 我们 | 说明 |
|---|---|---|---|
| 底栏内容高 | 107rpx | **114rpx** | = 18 上内边距 + 44 图标 + 6 间距 + 24 文字行高 + 22 下内边距 |
| 凸起圆直径 | 100rpx | **128rpx** | 用户指定；素材的圆与底栏等高，所以素材看着更"坐"进去 |
| 圆高出栏顶 | 11rpx | **36rpx** | = 128 − (114 − 22) |
| 圆下沿距栏底 | 20rpx | **22rpx** | **= 文字下沿**，两者对齐 |
| 顶角圆角 | ≈24rpx | 24rpx | 底栏顶部两角 |
| 描边 | 无 | **无** | 圆直接压在白色底栏上，不加白圈 |

### 6.3 关键实现约束

**圆的下沿必须与其它 tab 的文字下沿对齐，且用定位表达，不要写死数值：**

```scss
.raised {
  position: absolute;
  left: 50%;
  bottom: var(--tabbar-padding-bottom);  // = 22rpx
  transform: translateX(-50%);
}
```

这样以后改底栏高度或字号，两者不会跑偏。

### 6.4 结构

```
miniapp/src/custom-tab-bar/index.vue     ← 新建
miniapp/src/pages.json                   ← tabBar 加 "custom": true，
                                            list 保留 5 项（供 switchTab 用），
                                            selectedIconPath 清理掉
```

5 个 tab 页各自在 `onShow` 里同步选中态。客服页不在 tabBar 显示之列，但仍需保留在 `list` 里以便 `switchTab` 跳转。

### 6.5 页面底部安全区

自定义 tabBar 后，页面不再自动预留底栏高度。各 tab 页底部需自行留白：

```
底部留白 = 114rpx + env(safe-area-inset-bottom) + 16rpx
```

## 7. 图标体系

### 7.1 现状（**重要风险**）

- 项目**当前没有使用任何 `u-` 组件** —— uview-plus 装了、`main.ts` 里 `app.use(uviewPlus)` 注册了、`pages.json` 里配了 easycom，但从没用起来
- **没有 `src/uni.scss`**，`main.ts` / `App.vue` 里也没有 import uview-plus 的样式
- `u-icon` 的字体走远程 ttf：`https://at.alicdn.com/t/font_2225171_8kdcwk4po24.ttf`（55,940 字节）

**微信小程序 wxss 不支持远程 `@font-face`。** 所以直接上手写 `u-icon` 大概率在真机上显示成空白方块。

### 7.2 方案

把字体 **base64 内联**进项目（原始 55KB → base64 约 74KB，主包上限 2MB，可接受）：

1. 下载 ttf，转 base64
2. 生成 `src/styles/uview-iconfont.scss`，覆盖 `@font-face` 的 `src` 为 data URI
3. 在 `App.vue` 的全局 style 里 import

### 7.3 必须先验证（第 1 步就做）

在写任何页面之前，先做一个**最小验证**：在一个页面放一个 `<u-icon name="home" />`，用微信开发者工具在**真机预览**下确认图标可见。

如果内联方案不通，回退顺序：

1. `wx.loadFontFace` 动态加载（需在微信后台把 `at.alicdn.com` 加入 downloadFile 白名单）
2. 换成自绘 PNG 图标（`static/icons/`）

**在验证通过前，不要批量替换页面里的 emoji。**

### 7.4 图标映射

需要建立 emoji → u-icon 名的映射表（实测 **31 种**），放在 `src/utils/icon-map.ts`，作为纯数据可单测。

映射表要覆盖**全部 31 种**，避免漏掉某个页面时回退成 emoji —— 漏一个就是一处跨机型不一致。

## 8. 空状态与演示数据

### 8.1 空状态

`EmptyState.vue` 改造为使用 `u-icon` 的空状态插画（图标集内已有 `uicon-empty-address`、`uicon-empty-car`、`uicon-empty-coupon`、`uicon-empty-data`、`uicon-empty-favor`、`uicon-empty-history`、`uicon-empty-order`、`uicon-empty-search`）。

文案分场景，不只说"暂无数据"，给出下一步动作。

### 8.2 演示数据

```
miniapp/src/mock/demo-data.ts    纯数据集（分类 / 商品 / 案例 / 聊天话术）
miniapp/src/mock/fallback.ts     开关 + applyFallback() 判定逻辑
```

- 开关：`VITE_DEMO_FALLBACK` 环境变量。uni-app 会读取项目根目录的 `.env` / `.env.production`，所以落地上就是两个文件：`.env` 写 `VITE_DEMO_FALLBACK=true`、`.env.production` 写 `false`。代码里读 `import.meta.env.VITE_DEMO_FALLBACK === 'true'`
- 兜底：环境变量缺失时按 **false**（关闭）处理 —— 上线漏配的后果是"页面空"（用户看到空状态），比"线上展示假数据"轻得多
- 判定：接口返回**空集合**时替换为演示数据；**请求失败**时不替换（保持错误态可见，不掩盖真实故障）
- `applyFallback()` 设计为**纯函数** → 可用现有 vitest 直接单测

| **B3** | 新增种子数据脚本（分类 / 商品 / 案例 / 促销），幂等可重复执行 | 线上全空，5 个 tab 页没有任何内容可显示 | 跑两遍不产生重复数据 |

**B2 的具体清单：**

| 前端调用 | 后端现状 | 修法 |
|---|---|---|
| `GET /cases/tags/styles` | 不存在（被 `/{case_id}` 捕获 → 422） | 前端改调 `/cases/tags`，从返回的 `{category_tags, style_tags, area_ranges}` 里取 |
| `GET /cases/tags/categories` | 同上 | 同上 |
| `GET/POST /cases/{id}/like` | 后端不存在 | 待定：要么后端补 like 接口，要么前端去掉点赞 |
| `POST /auth/logout` | 后端不存在 | 待定：要么后端补，要么前端去掉（JWT 无状态，前端清 token 即可） |

> 后两项标「待定」是故意的——它们各有两个合理修法，取决于这功能要不要留。实现计划里必须先定，不能含糊过去。

### 本次不做

**前端**

- 剩下 **15 个**子页面（共 20 个页面 − 本次 5 个）：购物车、下单、订单详情/列表、地址、企业信息、会员、收藏、浏览记录、优惠券、设置、帮助、商品详情、案例详情等
- 交互/业务逻辑变更（除客服页不显示底栏外，页面行为保持现状）

**后端 —— 已确认存在、但本轮不修**

排查中确认的真实缺陷。它们影响的是本轮范围**外**的子页面（下单、结算、账期），本轮不动，记在这里避免遗忘：

| 缺陷 | 影响 |
|---|---|
| 取消 / 退款**不回滚库存** | 库存只减不增，长期虚低。下单是读-改-写、无行锁，并发下有超卖竞态 |
| 促销 `apply_promotion()` **全库无人调用** | 满减/折扣只活在单元测试里。**下单金额不受促销影响**——促销目前纯粹是展示 |
| `FLASH_SALE` 是死枚举 | `apply_promotion` 没有对应分支，会**静默返回原价**（不报错，最难查的那种） |
| 支付是**模拟的** | 微信支付直接置 `PAID`（代码里写着 `simulate for now`）；银行转账无管理员确认接口；全库无支付回调/webhook |
| 管理员 `PUT /orders/{id}/status` 可**绕过状态机** | 能任意设成 shipped/completed；`OrderStatus.CONFIRMED` 定义了却没用 |
| `credit`（账期）是半成品 | `check_credit` / `freeze_credit` 无人调用；`CreditBill` 永不生成，所以 `/credit/bills` 永远为空 |
| 下单**不清空购物车**、无购物车结算接口 | 前端得自己处理 |
| 无发货 / 物流 | `tracking_number` 字段没人写 |

> ⚠️ 注意 **B1 建了 `credit_bills` 表 ≠ 账期能用了**——账单生成代码根本不存在，建表只是让 schema 与模型对齐、消除 500。这是有意的：建表是零风险的卫生工作，而写账单生成逻辑是另一个功能。

**新功能 —— 本轮完全不做**

- **积分抽奖**：全库零代码（`积分|抽奖|lottery|points` 零命中）。这是独立新功能，需要自己的 spec → 计划 → 实现周期。
  另注：项目里的 `credit` 是**账期/授信**，不是积分，别混。

> §3.2 的全局圆角 token 变更会**间接影响**范围外的 **15 个**子页面，需做视觉回归。

## 10. 测试策略

项目已有 vitest（`environment: 'node'`，仅覆盖 `utils/` `api/` `stores/`，**没有组件测试环境**）。

### 后端（pytest）

后端已有 **29 个测试文件、159 个测试函数**，`tests/conftest.py` 用 SQLite 内存库 + `StaticPool`，每个测试函数重建表，通过 `dependency_overrides` 替换 `get_db`，**不依赖 PostgreSQL/Redis**。购物车（`test_cart_api.py`）和订单（`test_orders.py` 19 个、`test_order_actions.py` 15 个）覆盖扎实。

本轮后端改动配测试：

- **B1**：迁移测试——建表后 `promotions` 可查、`/promotions/active` 返回 200（现有 `test_promotions.py` 走 SQLite `create_all`，**不会发现生产缺表**，所以要单独测迁移）
- **B2**：契约测试——`/cases/tags` 返回结构断言；改了前端调用后，用后端测试锁住接口形状
- **B3**：种子脚本测试——**跑两遍断言不产生重复**（幂等性是这块最容易出错的地方）

> 注意：现有测试全跑在 SQLite 上，而生产是 PostgreSQL。JSON 字段筛选（案例标签用 `JSON.contains`）在两库行为有差异——B2 涉及的正是这块，改动要在 PG 上验证一次。

### 前端可单测（沿用现有 vitest，无需加依赖）

- `src/mock/fallback.ts` 的 `applyFallback()` —— 空集合替换、失败不替换、开关关闭时不替换
- `src/utils/icon-map.ts` 的映射完整性 —— 每个 emoji 都有对应 u-icon 名
- 新增/改造组件中的纯计算逻辑

### 不可单测（需人工验证）

- 组件视觉 —— 无 `@vue/test-utils` + jsdom 环境，本次**不引入**（会给全站 20 个页面引入测试基建，超出范围）
- 真机渲染 —— 图标字体、自定义 tabBar 凸起圆、横滑手势，均需微信开发者工具真机预览

### 验收方式

每个页面在**两种数据状态下**各看一遍：演示数据（满） + 真实空数据（空）。

## 11. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **u-icon 字体在真机不显示** | 全站图标空白，返工量大 | §7.3 的最小验证**作为第一步**，通过前不批量替换 |
| 全局圆角 token 影响 25 个范围外页面 | 出现压字/错位 | 实现阶段做一次全页面视觉回归 |
| 自定义 tabBar 后各页底部留白不一致 | 内容被底栏遮挡 | 统一用 §6.5 的留白公式，并加一个全局 mixin |
| 生产库无数据，真实效果无法验收 | 上线后才发现问题 | §8.2 演示数据 + 空状态双状态验收 |
| 案例横图卡依赖真实案例图 | 无图时观感差 | 空状态用品牌色几何底纹 + 插画兜底 |
| **B1 迁移写错会锁死生产部署** | 高——`alembic upgrade head` 失败会让整个部署流程中断 | 迁移必须先在干净库和 PG 上各跑一遍；`.superpowers/` 里有现成的 `test.db` 可参考但不作准 |
| B3 种子脚本不幂等，重复执行灌出重复数据 | 中 | 测试里跑两遍断言；脚本用"存在则跳过"而非"先删后插" |
| 后端测试跑 SQLite、生产是 PG，B2 的标签筛选两库行为有差异 | 中——测试全绿但线上仍可能空 | B2 改动必须在真实 PG 上手工验证一次 |
| 现有测试通过 ≠ 功能完整 | 中 | 已知缺口（库存不回滚、促销不接入）恰恰是测试没覆盖的；不要拿"测试全绿"当功能完整的证据 |

## 12. 未决项

设计侧**无**——所有设计决策已在评审过程中确认。

后端侧有 **2 项待定**，都是「这功能要不要留」的产品决定，不是技术难题：

| 待定项 | 选项 |
|---|---|
| 案例点赞 `/cases/{id}/like` | 后端补上 like 接口（要加表存点赞关系） / 前端去掉点赞 |
| 退出登录 `/auth/logout` | 后端补一个（JWT 无状态，实质只是占位） / 前端直接清本地 token |

这两项必须在**写实现计划之前**定下来，否则计划里会出现「视情况而定」这种没法执行的条目。
